# Prompt to 3D

## One prompt, optional extras (2026-09-10)

The opening page has one prompt and **Run with Grudge**. Expand **Hunyuan extras** to select Hunyuan 3D generation or Hunyuan Paint textures for that request. Both start off and reset after the request finishes. Grudge automatically analyses the request using the installed local `grudge-dev` model and operates the existing tools. Selecting an enhancement adds that explicit choice to the same request; it does not create a second required prompt.

**Tools & saved work** keeps manual utilities, history and route planning collapsed. Grudge can open the required controls itself. After a local creation completes, the tools close, the page returns to the prompt and one model panel shows the saved result. Model details and the action record stay collapsed. The model viewer and Hunyuan interface load on demand; a fresh session mounts neither an empty preview nor the neural workflow. Fresh profiles open on Prompt to 3D; existing saved routes and explicit handoffs remain supported.

Missing Hunyuan setup is reported within its optional workflow. It never disables ordinary native creation, editing, animation, saving or app controls. Existing provider installation and visual-review requirements apply when using those extras.

## Automatic Grudge prompt (2026-09-10)

The primary **Run with Grudge** prompt on `/prompt3d` automatically invokes the installed local `grudge-dev` model, observes the current app, and executes its existing controls. It shares the same controller and action record as **Ask Grudge**, so work continues when a request opens another page. Ctrl+Enter submits; Stop prevents further actions after an in-flight request returns. Typing alone never mutates an asset.

Creation, edits, materials, animation, managed saving, local files, Skeleton Studio, Forge and the other available app controls remain accessible independently of Hunyuan. For example, “Create a blue cube, make it spin, save it, then open it in Forge” uses the existing immutable creation service followed by the existing editor handoff. A trailing app instruction is kept separate from the asset builder. **Direct asset creation controls** retains the original manual prompt and settings.

**Optional Hunyuan enhancement** opens the retained neural workflow. Naming Hunyuan, TRELLIS or HY-Motion in a request also permits their existing controls. Ordinary requests and negated provider requests cannot activate that workflow. A saved neural preference or pending concept no longer replaces the default local workspace. Optional provider discovery runs only when its workspace or the advanced route planner is opened; it does not delay normal prompt startup. Exact neural source identity, licensing and visual-review requirements still apply to explicitly requested neural work.

The shared planner may start the already installed native Ollama CPU service on loopback when a submitted request needs it. It uses `grudge-dev` rather than substituting another model, downloads no weights, contacts no external model and does not reserve the GPU. If the installed runtime or model is missing, the prompt reports the problem and manual utilities remain usable. Existing service and app workloads are preserved.

**Advanced route planner** remains an optional deterministic inspection tool. Its default route uses existing local creation tools, including compound assemblies; neural providers must be explicitly chosen. Supported output still depends on the existing authoring utilities. A route being available does not promise arbitrary geometry or production-quality neural output. App control reaches the original controls, native open/save dialogs, folder browsing and creation, file inputs, text and confirmation dialogs, code editors, scroll areas, keyboard shortcuts and canvas pointer gestures. The Control window selector targets owned viewer and editor pop-outs. Native and browser/blob exports share the save workflow, and a save is complete only after the destination file exists. This change does not grant arbitrary shell access or bypass app access checks.

## Dialogs and native input (2026-09-10)

During a Grudge run, file and confirmation requests appear in the app's dialog panel. Enter a full destination or source path, browse folders, select multiple files where supported, create a folder, or cancel. Existing files require the Replace existing file option. Normal manual open/save calls retain Electron's dialogs; local text prompts use the accessible panel. Embedded editors retain synchronous text-prompt semantics through a narrow, bundled preload that exposes only a text request.

Keyboard and pointer input is sent to the observed app window, not the operating-system desktop. Canvas gestures use the existing viewport mapping: right drag orbits, left drag moves X/Y, middle drag adjusts camera position, and the wheel zooms. The controller reads the current camera position and target before verifying navigation. Code editors accept native selection, shortcuts and exact text insertion; scroll controls expose long panels and lists. The original app remains responsible for implementing each operation.

Every action retains its observed element, document and owner. Changed documents, replaced or covered controls, unrelated windows and foreign origins cannot receive stale input. Stopping dismisses only unanswered prompt dialogs and releases this controller's input hooks. Authentication and permissions still come from the original app. Sending, publishing, deleting and overwriting still require the corresponding user instruction. None of these controls depends on Hunyuan or another neural provider.

## Original creation in one flow (2026-08-31)

In **Prompt to 3D**, select **Original procedural CPU creator** as an explicit override or accept it when the quality-first router identifies it as the strongest ready route for a supported basic brief. Choose **Prop / Stylized** for a basic curved sword or cosmetic video-game gun prop, or **Character / Stylized** for an original segmented person. Enable the remembered local-controls checkbox once. The routed prompt box creates, textures and animates the current asset; **New asset** clears that selection without deleting history. There is no separate Object/Component panel or mandatory concept-selection stop. A blocked neural choice is disclosed and never silently replaced by procedural output.

The optional local planner consumes the prompt and selected Category/Style. Internal rules handle shape, attachment and supported motion; explicit category/style and creation method remain authoritative. With planning off, deterministic typed rules handle these basic examples without model inference. With planning on, an already installed local Ollama can propose schema-constrained planning fields using CPU and unload after the request. It is not a mesh generator, cannot execute code and does not download providers or weights. Planner-on behavior was not part of the passing nine-stage trial.

The verified short-prompt sequences are:

1. `Create a curved sword.` → `Texture it with appropriate textures.` → `Animate it swiping side to side.`
2. `Create an original basic video-game gun prop.` → `Texture it with appropriate textures.` → `Animate a visible projectile shooting from it.`
3. `Create an original person.` → `Texture it with appropriate textures.` → `Animate it doing a simple dance.`

Creation authors new geometry from code-defined primitives/parameters, never a borrowed model or render. Texturing adds authored pixel-pattern PNG maps embedded in the GLB. Follow-ups preserve the base geometry identity and earlier stages. The game projectile is a separately named effect mesh, not a change to the prop. The character has real hierarchical joint articulation, but its rigid segments are not a skinned/deforming production rig. Repeat prompts can produce the same deterministic design; this is original authoring, not a promise of a unique random object each time.

Each submitted stage receives a new `<generator-root>/creation-history/<attempt-id>/` directory containing its prompt/settings, status events and, on success, an immutable GLB, provenance and validation. All prior stages remain listed in **All attempts & saved revisions**. **Open / replay** makes that revision the current asset; **Reopen from local storage** reloads its saved GLB and embedded maps/clips without inference. Failed attempts have no replayable asset unless a valid completed artifact exists. No auto-purge is permitted. Neural jobs and older Forge revisions remain in their existing separate history folders.

The packaged `original-flow-2026-08-31.1` trial passed all three chains together through screen control and normal UI prompts, then reopened and played all three final local files. ## Cosmetic detail and bounded structural adjustment (2026-09-01)

After a textured and animated procedural asset is current, the same prompt box supports two additional operations. `Add detailed cosmetic additions to it.` authors new detail meshes appropriate to that asset. An **adjust** prompt changes supported named parts by deterministic bounded amounts. Both operations save a new immutable GLB and provenance record, keep the same asset ID, retain existing embedded textures and clips, and record the parent file hash plus previous and current geometry hashes. The source mesh is never replaced by a library or reference model.

The packaged UI trial used these exact prompts:

1. Sword: `Add detailed cosmetic additions to it.` → `Make its blade longer, wider and more curved; enlarge the guard.`
2. Game prop: `Add detailed cosmetic additions to it.` → `Make it longer and bulkier with a larger muzzle.`
3. Character: `Add detailed cosmetic additions to it.` → `Make the character taller and broader with a larger head.`

The sword enhancement adds a fuller/inlay, ricasso collar, guard caps and pommel inlays. Its adjustment changes blade length/width/curvature and guard width while preserving the grip-pivot swipe. The cosmetic game prop adds vent ribs, energy coils, a sight and side studs; its length/bulk/muzzle adjustment also moves the decorative projectile origin with the muzzle. The character adds shoulder plates, cuffs, a belt buckle, knee trim and boot trim; its height/breadth/head adjustment preserves the existing 12-node articulated dance.

The **Available refinements** box is the authoritative prompt hint for the current asset. The result card reports applied changes, detail nodes and previous/current geometry identity. These are bounded procedural operations rather than general image editing, arbitrary sculpting or semantic part recognition. Unsupported changes must remain unavailable or return an honest error; do not invent an approximate adjustment or silently switch creation methods.

## Mandatory Hunyuan concept approval and older Forge refinement

The separately selected installed Hunyuan route always generates and retains exactly one concept before geometry. A technically valid concept stops durably at **Awaiting explicit approval**; framing/background checks do not approve identity, resemblance, required parts or artistic quality. The review surface shows the exact retained image, current user prompt, compiled plan, seed, provider, AssetSpec revision, concept hash and effective presentation contract. That contract defaults to one complete centered subject, broad margins, neutral lighting, no support or scenery and a plain white background, while preserving an affirmatively requested stand, scenery, custom background or lighting as an explicit exception. Geometry cannot load until the reviewer records **pass** for identity/required parts, subject presentation, and framing/background/support, then clicks **Approve for 3D** for that exact hash-bound inspection. A failed check instead requires a retained classification: presentation, semantic anatomy/parts, prompt-negation misunderstanding, or other. Cropped or technically unusable concepts stop as retained technical failures. The preparation mask is a deterministic white-background cutout, not a general photo segmentation model, and no technical result may supply semantic approval.

**Regenerate concept with new seed** is available only after an explicit classified rejection, a retained deterministic technical failure, or a pending legacy-concept upgrade. It makes one concept only, increments the saved seed exactly once, disables textures and preserves the prior attempt, technical report, inspection, reason and exact successor prompt/plan/presentation/spec hashes in immutable history; it does not load geometry. **Edit rejected brief** restores and unlocks the authoritative saved brief, creates a separately linked attempt only after the brief actually changes, and **Cancel edit** restores the retained fields. Approval records the explicit action time/source and binds the job, attempt, image SHA-256, technical-report SHA-256, presentation contract, three-check inspection, prompt, seed, provider and canonical AssetSpec fingerprint. Root and variant AssetSpec records, `concept-prompt.json`, `concept-approval.json`, `concept-inspection.json`, job history and final provenance all use the same current prompt/plan/seed. Completed legacy assets remain reopenable, but an uncompleted legacy concept cannot gain geometry approval and must be freshly regenerated. Missing, stale, altered or contradictory report/inspection/approval/provenance data fails closed in history reload, provider execution and managed save/export validation.

The default finishing mode scales uniformly to height. Width and depth are reported instead of stretching the object to force a match. Raw provider meshes, concept images and cutouts are retained. Shape inference explicitly seeds the generator at 512 reconstruction resolution; simplification uses a 0.005 error bound and may fail an undersized triangle budget instead of destroying detail. Technical checks cannot establish likeness, completeness, watertightness or production suitability.

The local trials produced a complete recognizable neural longsword, but the concept model still ignored strong curvature and leaf-shaped blade requests. Do not describe those rejected trials as successful examples of their requested type. Full neural painting was not exercised with the occupied GPU; its existing headroom requirement remains intact.

**Texture & animate in local Forge** opens the existing workbench. Chat proposes a validated recipe; inspect the reversible preview, change region/width/curvature/pivot/duration controls, ask for another refinement, compare the original, then **Accept & autosave revision**. Each accepted revision saves a separate GLB and recipe under `<generator-root>/revisions/<uuid>/`. Files can be reopened through Local Files. These previews use procedural surface maps and rigid-object turntable/swing/thrust clips; they are not neural texture painting, skeletal animation or a production UV unwrap. Missing UVs get planar preview mapping.

For exact sword silhouettes, explicitly request a **precision longsword**, **precision sabre**, **precision leafblade**, or **precision rapier**. This separate parametric authoring path produces named blade, guard, grip and pommel parts and never substitutes itself for a selected neural provider. Type/length commands choose explicit dimensions; inspect and adjust all other proposed details before accepting.

Chat runs on local Ollama with CPU inference and `keep_alive: 0`. The connection is saved separately from other Ollama settings. **Local chat connection → Start installed CPU planner** starts an already installed native Windows Ollama on loopback port 11435 and reuses its existing model directory; it never downloads weights. The planning action itself does not start services. An unavailable model/service gives a visible error, with no cloud fallback.

Implementation references: [official Hunyuan shape preprocessing](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/82920d643c0dc2f7bfd7255f45f62d386edfe60c/hy3dshape/hy3dshape/preprocessors.py), [Ollama structured JSON schemas](https://docs.ollama.com/capabilities/structured-outputs).

The installed-neural-generators view turns a versioned `AssetSpec` into a provider-generated GLB, then post-processes and validates it before it can enter the existing asset pipeline. Its deliberate **Plan fields with local Ollama** action can propose only allowlisted JSON fields for the `AssetSpec`; it never starts Ollama, pulls a model, contacts a non-loopback host, changes the selected provider/route/coordinate contract, or executes model output. Ollama is not represented as a mesh generator and cannot emit shell commands, Blender scripts or Python for this workflow.

## Readiness states

- **Ready**: the preferred provider-native GPU profile, platform/software, signed install manifest and current run headroom pass.
- **Setup required**: the host can satisfy the backend but its isolated prerequisites or weights are absent/incomplete.
- **Busy**: setup is complete but current free VRAM is below the selected run mode.
- **Marginal**: a provider-native reduced-compute or CPU profile applies, has a pinned measurable threshold and exposes its visible speed/fidelity tradeoff. No provider is marked marginal merely from a model-name guess.
- **Unsupported**: a physical or platform constraint cannot be satisfied on the host.
- **Cloud only**: both local backends are genuinely unsupported. Missing setup or temporary GPU use never causes Cloud only.

The main process measures every NVIDIA adapter's UUID, index, vendor/model, total/free/used VRAM and compute capability, plus system RAM, destination disk, OS, WSL distributions, Python, Conda and CUDA toolkit before showing neural-provider download readiness. It chooses the first currently runnable provider-native profile in declared quality order. CUDA work is bound to the retained GPU UUID instead of assuming index 0; if current GPU headroom is insufficient, HY-Motion may select its official CPU mode only when the declared RAM threshold passes. A deliberate pre-download check and every neural pre-run check also probe the selected normal-user WSL distribution without reading its account name: Linux version, non-root identity, writable home and system Python must pass; CUDA visibility is required only for a selected CUDA profile. The default basic local animation route bypasses neural Install Options entirely and has no GPU/headroom gate. A model name alone never establishes compliance.

## Installer safety

The UI and `npm run prompt3d:install` use the same `Prompt3DInstaller`. It uses an immutable official revision for every source/model, verifies the official Git origin, refuses to overwrite a dirty source snapshot, uses a checksum-pinned `uv`, task-contained paths, bounded commands, resumable Hugging Face snapshots, task-owned WSL process groups for cancellation, recoverable removal and a local Ed25519-signed/hash manifest. The manifest binds every downloaded model file to a SHA-256 inventory and tree hash plus the source-dependency revisions and hashes of the isolated Conda explicit lock and `pip freeze`. Install/repair performs complete model-byte and runtime verification. Every Hunyuan geometry, Hunyuan Paint and HY-Motion run performs a fresh deep verification: the manifest signature, exact model file set, every model-file SHA-256, source origin/revision/cleanliness, isolated environment locks and importable runtime packages must all match before inference. It does not mutate global PATH and never installs on startup. License acknowledgement is per provider and cannot be accepted automatically; removal has a separate confirmation and never requires accepting the provider licence.

TRELLIS does not invoke the upstream `setup.sh`: the pinned upstream script references a removed `vox2seq` directory and clones several CUDA dependencies from moving branch heads. The typed installer instead obtains exact revisions of `utils3d`, `nvdiffrast`, `mip-splatting`, and the last upstream TRELLIS revision containing `vox2seq`; it pins xFormers, spconv and Kaolin, selects the xFormers/native-spconv path, and omits flash-attn and the unused octree renderer. The GLB path still installs every compiled extension it imports.

On Windows, setup may pause after `wsl --install -d Ubuntu-24.04 --no-launch`. Launch Ubuntu once and create its normal user, then choose **Repair / resume**. Do not substitute `docker-desktop` or a root-only bootstrap. Both provider environments stay separate under the normal Linux user's local data directory; no global PATH is changed.

`GRUDGE_PROMPT3D_ROOT` selects the Windows-side source/model/job root. The UI and CLI share its root-contained `.integrity` signing key so one entry point cannot invalidate the other provider’s manifest; partial or mismatched key material fails closed. `GRUDGE_PROMPT3D_WSL_DISTRO` optionally selects one exact normal-user WSL distribution after a storage migration; if omitted, the first non-Docker distribution is used. WSL virtual-disk placement is deliberately outside this installer, so changing either value never moves or re-registers a distribution.

## Job boundary

**Autosave and retention are on by default.** The local asset brief is saved by the main process as it changes and restored after navigation or restart; the renderer keeps a mirror for quick display. A Saved indicator appears after the persistent write succeeds. Each generation already uses its own output directory; an atomic `job-status.json` now retains its progress, validation report references and final state alongside the output. Older jobs can be recovered from their existing AssetSpec, output and validation files. The previous successful result stays visible until the next successful result is ready, including when a replacement fails. An interrupted run is shown as interrupted and requires a deliberate retry; it is never restarted automatically. The checkbox preference, draft and job history contain no capability secret. Autosave failures are displayed instead of being reported as success.

New privileged IPC calls require the exact main-window sender, the exact app origin and a window-scoped capability grant. **Enable local controls** is a single checkbox: the user's enabled/disabled choice is saved for this local application profile and restored after navigation or restart. It defaults to disabled for a new profile. A saved enable choice issues a fresh in-memory grant to the authorized main window; disabling clears the saved choice and revokes current grants. The preference and autosaved brief are stored in `prompt3d-preferences.json`, separately from importable workspace data; capability secrets are never stored there. The random grant secret stays in the main process; neither the renderer nor a webview can read it. Remembering the choice does not start a job, install models or accept provider licences. Jobs use one bounded loopback sidecar on `127.0.0.1`, concurrency 1, a 90-minute timeout and task-owned directories. Provider workers receive typed fields only. Cancellation signals the exact task-owned Linux worker PID and never terminates the shared WSL distribution. No renderer-supplied command or code is executed.

Reference conditioning is optional and remains local. The guided picker offers either one front image or exactly four authorized PNG, JPEG or WebP files, added individually in the fixed front, left, right and rear/back order. Each view is independently decoded, size-bounded, copied into the task before preflight, and bound by role, SHA-256, dimensions and media type to the concept approval, provider request, provenance, saved workflow and portable evidence bundle. The editor shows each retained thumbnail, role, dimensions and hash; replacement stays bound to that labelled slot. A typed provider capability requires a front view, distinct bytes and only the declared roles/count. One view uses Hunyuan3D 2.1. The complete four-view set loads the separately pinned official `tencent/Hunyuan3D-2mv` safetensors checkpoint and passes the labelled image dictionary directly to that pipeline. Missing, byte-duplicated, changed, tampered or undeclared sets are rejected; no image is discarded and no provider/model is silently substituted. Prompt-only batches remain prompt-only and cannot silently inherit a reference set.

The job record is created before preflight so the UI can explain the first wait. Its retained timing list covers job acceptance, hardware/headroom and WSL runtime readiness, signed-provider verification, sidecar health, provider/model warm-up, concept inference, concept review, explicit approval, geometry start/inference, post-processing and validation. Before signed-provider verification or inference, the selected output filesystem must have the stage's conservative estimated headroom: 0.50 GiB for concept preparation, 3.00 GiB for geometry generation and validation, and 4.00 GiB for Hunyuan Paint texture generation and validation. The message identifies the exact selected location, measured free space, estimated allowance and recovery action; actual use varies by asset. An installed provider does not bypass this output-space gate. The sidecar process is reused while healthy; provider model processes still exit after each job so they release GPU memory and the next run can enforce fresh headroom. A concept crop/background rejection is a distinct concept-quality failure: the generated image and review metadata stay in history, geometry is not loaded, and the only retry helper is a user-clicked concept-only run with seed +1. A technically valid Hunyuan concept is also not geometry-ready: it remains pending until the separate exact approval action is durably recorded and fresh pre-run checks pass.

Hunyuan execution is capability-based per operation. Geometry prefers the full 512-octree GPU profile when current VRAM permits, then the provider-native offloaded 256-octree GPU profile, then genuine 256-octree CPU inference when measured system RAM permits. Texture exposes one six-view profile at the upstream-supported 512 px generation resolution, 2048 px render size and a bounded 1024/2048 px retained map. It requires the upstream-recommended 21 GiB free VRAM; lower unvalidated resolutions are not offered. Every profile uses the pinned local Hunyuan provider and is named in status, job input, result, provenance and lineage. If none fits the current machine or headroom, generation stops with the measured requirements instead of substituting another implementation.

Default concept presentation is one complete isolated subject on plain white, centred and fully visible, without a stand, text, scenery or unrelated object. Short natural-creature prompts keep a compact positive small-subject, full-body, white-background and broad-margin clause after the species/anatomy brief so long ears, feet, wings and tails receive usable edge clearance before the deterministic crop check. A foreground mask that reaches the provider image boundary is rejected because missing pixels cannot be recovered. A close but fully isolated subject is safely scaled and centred inside a broad working margin while the untouched provider image and its hash remain retained; this technical repair never replaces the required human semantic review. The compiler treats presentation/isolation constraints separately from subject detail, and explicit custom presentation may override the background or lighting defaults. Negated terms are retained as exclusions and are never promoted into positive subject clauses; generated concepts that nevertheless depict a forbidden item or omit a required relationship must be rejected and regenerated at the visual gate.

Each technically valid generated geometry, Hunyuan Paint texture revision and animation revision stops for a separate backend-persisted visual decision bound to that exact job, asset bytes, geometry hash and retained provenance. Approval and rejection are distinct actions: rejecting a texture or animation records a classified, hash-sealed `visual-rejection.json`, hides the failed preview and unlocks a corrected sibling from the exact approved parent. A merely unapproved result is never assumed to be rejected. Animation recovery always replaces the rejected clip set instead of appending it, so the failed clip cannot remain the default playback result. A later prompt cannot silently stand in for either decision. After base geometry approval, an individual workflow may choose **Use the existing generated model** and proceed to texture without shape refinement; that explicit action is hash-bound to the exact approved first Hunyuan variant and revalidated throughout save, export and reopen. Shape refinement remains available and is still mandatory in strict serial acceptance. After one approved Paint result, a manual workflow may explicitly retain that exact locally saved texture and continue to animation; optional texture refinement remains available. The first approved prompted animation advances the normal manual workflow to the final save/export/reopen panel, which also offers optional animation refinement or append and a direct route back to save without altering the approved result. Manual saving and export fail closed unless the sealed lineage starts at approved Hunyuan generation, includes either approved shape refinement or the explicit existing-model decision, contains a changed deep-verified Hunyuan Paint result, and ends at an exact visually approved animation whose provenance names its real route. The basic deterministic/local-library routes may therefore produce a labelled local game asset, but only genuine deep-verified HY-Motion may be represented as HY-Motion. The strict six-item acceptance batch rejects all basic fallbacks and separately retains the original requirements for prompted shape refinement, two texture prompts and two animation prompts per item; HY-Motion's upstream human/humanoid limitation remains authoritative.

During the explicit animation action, installed loopback Ollama performs only a schema-constrained capability and negation check. It must prove that the approved subject is one human or clearly humanoid biped and decide whether horizontal root travel was affirmatively requested; it does not create motion. The complete prompt, seed and bounded duration then go to the pinned official HY-Motion 1.0 Lite diffusion model. The provider's native right-handed +Y-up/+Z-forward 22-joint rotations and root trajectory are retained as a separate hashed artifact and mapped directly to the existing Mixamo-25 core. A generic local nearest-bone skin is created only when the approved mesh has no rig; append reuses that exact retained rig. Validation requires a skin, 22 unique joints, normalized four-weight vertex influences, inverse-bind matrices, a skinned surface and 22 generated bone-rotation channels while proving that source geometry and Hunyuan Paint material fingerprints are unchanged.

The HY-Motion task also contains the exact automatically selected execution profile. The worker accepts only the declared CUDA-standard or CPU-basic profile. CUDA selection sets the retained NVIDIA UUID for the isolated process; CPU selection invokes the upstream runtime's official `force_cpu` path, hides CUDA from that process and applies the retained reduced validation-step schedule. The generated motion artifact repeats this evidence, and binding fails if its profile, device, steps or GPU UUID differs from the measured task. This changes compute placement and inference depth only: it does not download a different model, generate canned movement, invoke a cloud provider or weaken visual approval.

Walking, running, dancing, hopping and similar action words alone do not authorize horizontal root travel. HY-Motion still generates their full joint action, but the binder removes horizontal root displacement unless the prompt explicitly asks the whole subject to travel in a direction, along a path or by a distance. Negative wording such as “do not move forward” is retained as a constraint and cannot authorize movement. The same negation-aware rule governs basic CPU anatomy, stance and motion classification: “not a rabbit” cannot select rabbit anatomy, “must not be standing” cannot authorize automatic upright bone placement, and mixed body plans stop for review. Conflicting direction clauses fail before inference. When HY-Motion is selected, props, weapons, quadrupeds, snakes, fish, birds and other non-humanoids fail with an unsupported-rig explanation; no basic morph, library clip or whole-model transform substitutes for HY-Motion or strict acceptance.

Outputs are scaled to the declared metre contract, use a stable `GrudgeAssetRoot`, declare +Y up and +Z forward, and receive provenance. New jobs place the selected attachment point at the origin; legacy jobs retain ground-centre placement. Validation checks GLB structure, finite geometry, world-space rendered dimensions and transforms, root/origin/axes, normals, UV/material/texture references, triangle/texture budgets and requested collision/LOD gates. Marked generated effects such as an animated trail are still checked for finite triangle topology but do not enlarge the base object's dimensions or impose another Hunyuan texture requirement. A failed check moves the GLB to quarantine. It is never uploaded or published.

Saved-model camera presets fit the asset's projected width and height for the selected view, including long tails and tall ears, with a small safety margin. The full-preview control remains available for closer inspection.

## Internal object and component rules

The user selects **Category** and **Style**, not another parallel classification panel. Object/component knowledge is internal to planning and shared compilation; explicit category/style choices remain authoritative. The current user prompt remains the single saved brief. Neural geometry conditioning is compiled in shared code and sent identically to the renderer preview and provider worker, without appending cinematic lighting, backgrounds, multiple views or ornamental prose. Existing stored rule data remains retained for provenance and compatibility; it is not a new required user step.

Whole swords use hilt/pommel down and blade up; axes/striking weapons use grip down and head up; polearms/staffs use shaft butt down. These default to the lower end at Y=0. Bow grips and shield mounts default to their central bounds point. Blades use their lower tang end; heads and guards use a centred socket/slot; pommels use the top mounting point, leaving their body below Y=0. Buildings and fixtures use their support base.

**Neural placement is numerical, not semantic recognition.** The compiled or previously stored origin percentages select a point in oriented bounds; that point becomes (0,0,0), with a `GrudgeAttachment` node and provenance. Collision centres follow the translation. Technical checks verify the requested point/marker and warn that actual hilt/socket location, complete geometry and orientation need human inspection. The system cannot prove a neural model followed the object rules. Mandatory Hunyuan approval requires exact matching conditioning, current prompt, seed, provider, spec and retained image hash. Original procedural assets instead have known authored parts, including the sword's grip pivot and the game prop's muzzle direction.

Neural vehicle generation remains disabled pending suitable wheel/topology/facing contracts. Creature geometry is enabled only through the explicit Hunyuan concept route and its exact semantic approval gate. Prompted creature motion separates body action from placement: walk, run, swim, slither and fly stay in place unless the prompt affirmatively names a direction, path or measured displacement; an undirected hop rises and lands at its starting position. Negated direction, vertical lift, spin, flap and trail wording is retained as a constraint. Directional defaults scale from the current generated asset rather than using a fixed multi-metre path. Deterministic, geometry-segmented operators provide continuously weighted grounded alternating strides, crouch/bend motion, whole-body waves, rear-weighted propulsion, bilateral flaps, squash/stretch and anchored distal swings. These generic operators add animation data to the generated mesh; they do not claim skeletal rigging, skin weighting, automatic anatomical recognition or semantic proof. Validation proves that a requested directional path moves, return-to-start placement closes, in-place motion has no generated root translation, vertical hops land, and every requested morph has both measurable vertex displacement and active animation weights. Every generated shape and motion still requires visual approval.

## Future roadmap: hybrid guided generation

Local user-supplied reference images are now implemented. CPU-procedural blockouts, user-supplied models, generated masks/depth/part IDs and automatic visual comparison against every supplied view remain planned work rather than validated current capabilities. Any future extension must retain provenance/licensing and immutable revisions and allow refinement without silent cloud fallback. The same allowlisted typed command contract should be exposed through text first, with optional local speech-to-speech later.

Arbitrary Google scraping is explicitly out of scope. Web search may discover candidate references, but the tool may ingest only user-owned, permissively licensed, or otherwise authorized inputs.
